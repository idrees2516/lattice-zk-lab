     7→ Abstract
     8→ A memory checking argument enables a prover to prove to a verifier that it is correctly processing
     9→ reads and writes to memory. They are used widely in modern SNARKs, especially in zkVMs, where the
    10→ prover proves the correct execution of a CPU including the correctness of memory operations.
    11→ We describe a new approach for memory checking, which we call the method of one-hot addressing
    12→ and increments. We instantiate this method via two different families of protocols, called Twist and Shout.
    13→ Twist supports read/write memories, while Shout targets read-only memories (also known as lookup
    14→ arguments). Both Shout and Twist have logarithmic verifier costs. Unlike prior works, these protocols do
    15→ not invoke “grand product” or “grand sum” arguments.
    16→ Twist and Shout significantly improve the prover costs of prior works across the full range of realistic
    17→ memory sizes, from tiny memories (e.g., 32 registers as in RISC-V), to memories that are so large they
    18→ cannot be explicitly materialized (e.g., structured lookup tables of size 264 or larger, which arise in Lasso
    19→ and the Jolt zkVM). Detailed cost analysis shows that Twist and Shout are well over 10× times cheaper
    20→ for the prover than state-of-the-art memory-checking procedures configured to have logarithmic proof
    21→ length. Prior memory-checking procedures can also be configured to have larger proofs. Even then, we
    22→ estimate that Twist and Shout are at least 2–4× faster for the prover in key applications.
    23→ Finally, using Shout, we provide two fast-prover SNARKs for non-uniform constraint systems, both of
    24→ which achieve minimal commitment costs (the prover commits only to the witness): (1) SpeedySpartan
    25→ applies to Plonkish constraints, substantially improving the previous state-of-the-art protocol, BabySpar-
    26→ tan; and (2) Spartan++ applies to CCS (a generalization of Plonkish and R1CS), improving prover times
    27→ over the previous state-of-the-art protocol, Spartan, by 6×.

   112→1 Introduction
   113→A zero-knowledge virtual machine (zkVM) is a cryptographic protocol that allows an untrusted prover to
   114→succinctly prove that it correctly ran some computer program Ψ on a witness. In a zkVM, the computer
   115→program is specified to run on a specific CPU architecture, which is also called a virtual machine (VM) or an
   116→instruction set architecture (ISA). In a zkVM proof, the prover proves that it correctly ran Ψ cycle-by-cycle.
   117→Generally speaking, zkVMs produce short proofs and have fast verification. Even if the zkVM first produces a
   118→proof π that is moderately large, π can be generically shrunk via SNARK composition. This means generating
   119→a smaller proof π ′ that establishes that the prover knows a valid π. Accordingly, the bottleneck in zkVM
   120→performance is prover runtime. zkVM provers today remain hundreds of thousands of times slower than
   121→native execution (i.e., the amount of work done to generate a proof π relative to that required to simply run
   122→Ψ with no proof of correctness).
   123→
   124→Background on zkVMs and memory checking. zkVM provers prove that they did two things correctly,
   125→over and over. They first prove the correct execution of the “fetch-decode-execute” logic of the VM, once per
   126→cycle. Second, they prove that reads and writes to registers and RAM were executed faithfully.
   127→A state-of-the-art zkVM, called Jolt [AST24], turns almost everything a VM does into reads and writes to
   128→memory. This includes the “fetch-decode-execute” logic of the VM. Roughly speaking, Jolt turns “fetch and
   129→decode” into a lookup into a read-only memory storing the program bytecode. Meanwhile, executing each
   130→primitive instruction is done via a lookup into a gigantic pre-determined table of size 264 . Jolt accomplishes
   131→this by using Lasso [STW24], which internally turns this one lookup into a giant table into a short sequence
   132→of lookups into smaller tables, and combines the results to get the output of the instruction.
   133→In summary, a key bottleneck for zkVM provers, and for the Jolt prover in particular, is proving that it
   134→correctly processed all reads and writes to memory. The fastest known methods for this task are called
   135→offline memory checking techniques. These techniques date back to work of Lipton [Lip89, Lip90] and
   136→Blum et al. [BEG+ 91]. In the context of zkVMs, offline memory checking techniques allow a prover to commit
   137→to a constant number of values, and perform a constant number of field operations, per memory operation
   138→performed by the CPU. Jolt currently uses Spice [SAGL18] as its memory-checking argument for registers
   139→and RAM, and Lasso [STW24] for read-only memories.
   140→
   141→Our contributions. We describe a new approach to memory-checking that improves significantly on offline
   142→memory checking techniques, promising substantial end-to-end speedups for zkVM provers. For reasons that
   143→will become clear, we call our approach the method of one-hot addressing and increments.
   144→We instantiate this method via two different families of protocols, called Twist and Shout. Twist supports
   145→read/write memories, while Shout targets read-only memories (also known as lookup arguments).1 Both
   146→families are parameterized by an integer d ≥ 1. The smaller the memory, the smaller d can be, and the
   147→cheaper each memory operation is for the prover as a result.
   148→Twist and Shout significantly improve on prior works across the full range of realistic memory sizes, from tiny
   149→memories (e.g., 32 registers as in RISC-V), to read-only memories that are so large they can’t be explicitly
   150→materialized (e.g., structured lookup tables of size 264 or larger, as arise in the Jolt zkVM).
   151→Detailed cost analysis shows that Twist and Shout are over 10× cheaper for the prover than state-of-the-art
   152→memory-checking procedures configured to have similar proof length. Prior memory-checking procedures can
   153→also be configured to have larger proofs. Even then, we estimate that Twist and Shout are (at least) 2–4×
   154→faster for the prover.
   155→Not only do Twist and Shout significantly speed up the prover across all practical memory sizes, they also give
   156→the prover a cost profile that more closely matches real CPUs. Unlike offline memory-checking techniques,
   157→the method of one-hot addressing is significantly faster for small memories than big ones, and Twist is faster
   158→for sequences of memory accesses with high locality (see Section 8.2.3 for details). This means that existing

   168→At the highest level, Twist and Shout leverage the power of the sum-check protocol [LFKN90] to minimize the
   169→amount of data the prover has to commit to, and to prove satisfaction of very large but very sparse constraint
   170→systems (i.e., a huge number of witness variables, but almost all of them are 0) while only “paying” for the
   171→sparsity of the witness (number of non-zeros) rather than the size of the witness.

   173→The parameter d: where it comes from and what it buys. When applied to memories of size K,
   174→the prover in the simplest variations of Twist and Shout commits to K − 1 0s and a single 1 per read or
   175→write operation. This makes these protocols especially efficient when combined with elliptic-curve-based
   176→commitment schemes, which are uniquely fast at committing to 0s: any committed 0s literally do not alter
   177→the commitment so they are free to commit, and committing to a 1 requires a single group operation requiring
   178→only 6–7 field operations. This performance profile is an excellent fit for the Jolt zkVM for RISC-V [And17],
   179→which currently achieves state-of-the-art prover performance and uses elliptic curve commitment schemes
   180→(specifically, HyperKZG [ZSC24] or Zeromorph [KT23]).
   181→However, even when 0s are free to commit to, large memories are problematic for the simplest instantiations
   182→of our methods, primarily because the commitment key (which must be stored by the prover) gets very
   183→large.2 To address this, we describe an entire family of protocols in which, for any desired integer d ≥ 1, the
   184→prover only commits to roughly d · K 1/d 0s per read or write operation. Using a large value of d comes at a
   185→cost: the prover also commits to d 1s per read or write operation, and each committed 1 forces the prover to
   186→perform one group operation. Hence, large values of d mean vastly fewer 0s are committed, which keeps the
   187→commitment key size bounded, but it also means slightly more 1s are committed, which modestly slows down
   188→the prover. Larger values of d also increase the amount of work the Twist and Shout provers do “outside
   189→of commitments”, and proof size grows linearly with d too. So one wants to choose d as small as possible,
   190→subject to the constraint that the commitment key is not too large.
   191→Choosing a value d ≥ 2 renders our methods suitable for memory sizes K in the millions or billions. It also
   192→allows our techniques to be productively instantiated with hashing-based multilinear commitment schemes
   193→over binary fields like Binius [DP23], FRI-Binius [DP24], and Blaze [BCF+ 24]. Even though committing to
   194→0s is not “free” with these schemes, committing to values that are known a priori to be in {0, 1} is cheap
   195→enough that our results still offer improvements over prior works.3 For these commitment schemes, d should
   196→be set just large enough to ensure that commitment time is not a prover bottleneck.
   197→Since the Twist and Shout provers commit to dK 1/d bits per address, to ensure committing with a hashing-
   198→based scheme is sufficiently fast, dK 1/d should be between a few dozen and a couple hundred bits, with larger
   199→memories leading to larger values of d (and more committed bits).
   200→To summarize, in applications we expect d to be between 1 and 4 if using an elliptic curve commitment
   201→scheme and between 1 and 16 if using a binary-field hashing-based commitments. Larger memories necessitate
   202→larger values of d. See Section 2.8 for details.

   204→The high-level ideas of Twist and Shout. A simple observation underlying Twist and Shout is that
   205→when memory addresses are specified in one-hot form, correctness of reads and writes becomes equivalent to
   206→very simple (i.e., rank-one) constraint systems. This observation is already explicit in prior works on lookup
   207→arguments [ZBK+ 22, ZGK+ 22, STW24, GM24].
   208→These constraint systems can be directly checked for correctness via the standard sum-check-based zero-check
   209→PIOP for, say, R1CS (see Section 3.6 for details). But there is a challenge: the constraint systems are very
   210→large, so large that we cannot tolerate a prover that runs in time linear in the number of witness variables,
   211→since for T operations into a memory of size K, there are (more than) K · T witness variables. Fortunately,
   212→the constraint systems are highly sparse: although they involve a huge number of variables, only about T

   223→ in roughly O(K + T ) time rather than O(K · T ) time. Roughly speaking, the sum-check prover does not
   224→“pay” for 0-variables, and neither does the prover when committing to those variables, at least when using a
   225→ curve-based commitment scheme.
   226→On top of this, for very large but “structured” read-only memories, where K = T C with C ≥ 1, by invoking
   227→(and generalizing) the sparse-dense sum-check protocol from the Generalized-Lasso protocol [STW24], we can
   228→implement Shout’s sum-check prover in time O(C · T ) ≪ O(K + T ).
   229→When using parameter d > 1, Twist and Shout further exploit that every “one-hot” vector (meaning a vector
   230→in {0, 1}K with exactly one entry equal to 1) can be expressed as a tensor product of d smaller one-hot vectors,
   231→each of length K 1/d . We use this to control the negative effects of large memory sizes K, especially the size of
   232→the commitment key when using curve-based commitment schemes and the total number of committed bits
   233→when using hashing-based commitment schemes. This does come at the cost of higher-complexity constraints
   234→in the resulting constraint systems: they change from rank-1 to rank-d.
   235→Twist needs to overcome an additional obstacle that threatens to bring in a Θ(K · T ) cost to the prover’s
   236→runtime in the context of read/write memory. Specifically, a natural first attempt at designing Twist involves
   237→the prover committing to the value of every register at every cycle. This would be K · T committed non-zero
   238→values. Twist addresses this by instead having the prover commit to increments: the difference in value for
   239→each register cycle-by-cycle. Since at most one register is written per cycle, this entails committing to only T
   240→rather than K · T non-zero values (moreover, all T of these non-zero values are “small” and hence fast to
   241→commit to). At the end of the sum-check protocol, when the verifier needs to compute a random evaluation
   242→of (the multilinear extension of) the register values themselves, we offload that evaluation to the prover with
   243→a second invocation of the sum-check protocol that relates the register values to the increments. At the end
   244→of that sum-check, the verifier needs to evaluate the multilinear extension of the increments at a random
   245→point, which it can do because the increments themselves were committed.
   246→We give two different implementations of the Twist prover. An important property of one of them is that the
   247→prover is faster when memory operations are local. Roughly, for a read or write operation to a memory cell
   248→that was accessed at most 2i time steps prior, the Twist prover performs only O(i) field multiplications to
   249→process that operation, less than the O(log K) multiplications that the prover performs per memory operation
   250→in the worst case. In order to achieve this, this variant of the Twist prover binds variables in a different order
   251→than the Shout prover: the Twist prover binds “cycle-count-specification” (i.e., time) variables first, rather
   252→than “memory-address-specification” (i.e., memory) variables. This ensures that in the first log K rounds,
   253→temporally-close accesses to the same memory cell quickly “coalesce”, which is what allows the prover to
   254→benefit from locality of memory access. In other words, by binding time variables first, the sparsity (i.e.,
   255→number of non-zeros) in the vectors the prover is processing falls quickly round-over-round when memory
   256→accesses are local, and the prover’s runtime in each round grows only with the number of non-zeros in these
   257→vectors.

   259→Fast-prover SNARKs for non-uniform constraints. We also use Shout to give two new, fast-prover
   260→SNARKs for non-uniform circuits or constraint systems. We call these SNARKs SpeedySpartan and Spartan++.
   261→Both offer a a significant improvement in overall prover time relative to the previous state of the art,
   262→BabySpartan [ST23], and in particular a 4× improvement in commitment costs. In SpeedySpartan and
   263→Spartan++, the prover commits to the witness (the solution to the constraint system), and nothing else.
   264→(At least this is the case when using polynomial commitment schemes with fast evaluation proof generation,
   265→e.g., Hyrax [WTS+ 18], Dory [Lee21]). For other schemes like HyperKZG, Zeromorph, and Bulletproofs/IPA,
   266→evaluation proofs themselves require committing to a linear amount of data.)
   267→SpeedySpartan is concretely faster than Spartan++, due primarily to SpeedySpartan’s use of a lookup table that
   268→is quadratically smaller than the one used by Spartan++. Hence, we consider SpeedySpartan to be of practical
   269→interest and Spartan++ to be primarily of conceptual interest (although even Spartan++ is concretely almost
   270→an order of magnitude faster than Spartan itself [Set20]). Spartan++’s most interesting performance property
   271→is that its prover’s commitment costs grow linearly with the number of multiplication gates in the circuit and
   272→not the total gate count (i.e., addition gates do not contribute to commitment costs). But both SpeedySpartan
   273→

   277→property of Spartan++ does not translate to major improvements in concrete costs.

   279→The high-level ideas of SpeedySpartan and Spartan++. SpeedySpartan and Spartan++ observe that
   280→correct processing of circuit wires boils down to lookups. By circuit wires here, we mean which gate outputs
   281→need to be treated as inputs to which other gates.
   282→There are two different ways this reduction from wires to lookups can be done. One technique originates
   283→in Spartan and its use of the Spark sparse polynomial commitment scheme [Set20]. The other originates in
   284→BabySpartan [ST23]. SpeedySpartan is a major refinement of the BabySpartan approach, while Spartan++ is
   285→a major improvement of the Spartan/Spark approach.
   286→In the case of SpeedySpartan, BabySpartan already showed that each input to any gate can be computed
   287→with a lookup into the table that stores all gate outputs. BabySpartan invokes Lasso as the lookup argument.
   288→SpeedySpartan replaces Lasso with Shout. We further observe that this replacement allows certain polynomials
   289→that were explicitly committed by the BabySpartan prover to instead be virtual : they are not committed by
   290→the prover, and Shout nonetheless allows the verifier to evaluate these polynomials at the necessary evaluation
   291→point. This leads to a 4× reduction in commitment costs, with field work improvements coming from the
   292→improved efficiency of Shout relative to Lasso.
   293→In the case of Spartan++, we directly give a major improvement of the Spark sparse polynomial commitment
   294→scheme. In its evaluation proofs, Spark has the prover prove it correctly ran a fast algorithm for evaluating
   295→the committed sparse polynomial at the requested evaluation point (see [STW24, Section 3.1] for details of
   296→this view of Spark). This algorithm performs lookups into a large table that stores evaluations of multilinear
   297→Lagrange basis polynomials at the requested (random) evaluation point. Spark effectively applies the Lasso
   298→lookup argument to this table. This requires the prover to commit to two random values per non-zero coefficient
   299→of the sparse polynomial (these random values are the results of lookups into “subtables” decomposing the
   300→large table). We replace Lasso with Shout, and further observe that this allows for the values returned by the
   301→lookups to be virtual polynomials. This eliminates the major prover bottleneck in Spark.
   302→To summarize, SpeedySpartan and Spartan++ use lookups in very different ways to deal with circuit wires.
   303→For circuits with n gates, SpeedySpartan computes a gate’s inputs via lookups into the size-n table storing all
   304→gate outputs. Spartan++ performs lookups into a size-n2 table storing all evaluations of multilinear Lagrange
   305→basis polynomials at a random evaluation point. Spartan++ pays increased costs relative to SpeedySpartan
   306→because the lookup table it uses is quadratically bigger, its use of the larger table does enable its commitment
   307→costs to grow linearly only with the number of multiplication gates.

   310→2 Overview of Twist and Shout and their costs
   311→2.1 Background
   312→zkVMs and Jolt. The RISC-V instruction set architecture involves 32 registers. In each CPU cycle,
   313→at most two registers are read and one is written. The Jolt zkVM [AST24] forces an untrusted prover to
   314→correctly process reads and writes to registers (and random access memory) using an offline-memory-checking
   315→procedure called Spice [SAGL18]. Spice’s application in Jolt currently accounts for about 20% of total prover
   316→time today, with most of this cost coming from registers (which are read and written nearly every CPU cycle,
   317→unlike RAM, which is accessed only via explicit load and store instructions).
   318→On top of the cost of Spice for checking registers and RAM, another 25% of Jolt prover time is spent on
   319→Lasso [STW24], an offline-memory-checking procedure tailored to read-only memories. Jolt uses Lasso to
   320→ensure the prover correctly executes the appropriate primitive RISC-V instruction during each CPU cycle (Jolt
   321→turns primitive instruction execution into a handful of lookups into fixed tables of size about 216 ). So in
   322→total, the Jolt prover currently spends almost half of its time in offline-memory-checking procedures. We
   323→anticipate that the fraction of Jolt’s prover costs will grow substantially over time, as other parts of the Jolt
   324→protocol continue to be optimized.

   329→Polynomial IOPs and polynomial commitments. As with most SNARKs, Jolt consists of a polynomial
   330→IOP (PIOP), which can be combined with any polynomial commitment scheme (for multilinear polynomials,
   331→in the case of Jolt) to obtain a SNARK. A polynomial IOP is an interactive protocol where the prover is
   332→allowed to send one or more large polynomials to the verifier, but the verifier is only allowed to query those
   333→polynomials’ evaluation at, say, a single randomly chosen point.
   334→A polynomial commitment scheme is a cryptographic protocol specifically designed to transform any polynomial
   335→IOP into a succinct argument. Specifically, rather than having the polynomial IOP prover explicitly send
   336→large polynomials to the verifier, a polynomial commitment scheme allows a prover to succinctly commit
   337→to those polynomials, and later reveal only the evaluations of the polynomials that are queried by the
   338→verifier (along with evaluation proofs, which prove that the returned evaluations are indeed consistent with
   339→the committed polynomials). One can render the succinct argument non-interactive with the Fiat-Shamir
   340→transformation [FS86a].
   341→Jolt uses multilinear polynomial commitment schemes based on elliptic curves, like HyperKZG [ZSC24] and
   342→Zeromorph [KT23]. The commitment to a polynomial of size n with these schemes consists of a single group
   343→element, and evaluation proofs consist of O(log n) group elements.4 In the future, Jolt plans to incorporate
   344→support for hashing-based commitment schemes over binary fields.
   345→
   346→Costs of elliptic-curve-based commitments. When a polynomial IOP is combined with an elliptic
   347→curve commitment scheme (e.g., HyperKZG [ZSC24]), the vast majority of the work done by the prover
   348→consists of elliptic curve group operations and finite field operations (over the field F used by the polynomial
   349→IOP, which is also the scalar field of an elliptic curve). For small memories, the method of one-hot addressing
   350→substantially lowers both the number of field operations over F and the number of group operations performed
   351→by the prover.
   352→There are two facts about elliptic curve commitments that the method of one-hot addressing takes heavy
   353→advantage of. The first is that committing to 0s is “free”. That is, when committing to a vector v ∈ Fℓ ,
   354→any i for which vi = 0 literally does not affect the commitment, and can just be “ignored” by the prover
   355→when computing the commitment to v. The number of committed 0s does influence some other prover costs
   356→arising in the protocol, especially the size of the commitment key, but it does not influence commitment time.
   357→Fortunately, the effect of the 0s on these other costs can be controlled, see Section 3.1 for details. Hence, in
   358→this informal overview it is both clearest and reasonably accurate to treat committed 0s as literally free for
   359→the prover. Second, small (but non-zero) values are cheap (but not free) to commit to. For example, any i
   360→such that vi = 1 costs the prover just one group operation when computing the commitment.
   361→For simplicity, in this work we consider any value in {0, 1, . . . , 232 − 1} to be “small”. We select the threshold
   362→of 232 − 1 as the limit of smallness for convenience of accounting: most zkVMs today use 32-bit data types,
   363→and so registers store arbitrary elements of {0, 1, . . . , 232 − 1}.5 Since the prover has no choice but to commit
   364→to the values read from or written to registers, it is convenient to call these values small. But this is also a
   365→reasonable notion of smallness: at practical instance sizes, committing to a 32-bit value with an elliptic curve
   366→commitment scheme takes roughly two group operations via Pippenger’s bucketing algorithm6 . This is much
   367→cheaper than committing to an arbitrary field element, which can require a dozen group operations or more.7
