Symphony: Scalable SNARKs in the Random Oracle Model
         from Lattice-Based High-Arity Folding
                                           Binyi Chen

                                      Tsinghua University∗


                                        August 20, 2026



                                               Abstract
           Folding/Accumulation schemes are a powerful tool for building scalable proof sys-
       tems. However, standard approaches for leveraging folding schemes, such as IVCs or
       PCDs, require embedding hash functions (modeled as random oracles) into recursive
       circuits, introducing both security concerns and significant proving overhead.
           We re-envision how to use folding schemes, and introduce Symphony, the first
       proving paradigm that leverages folding schemes as a black box without embed-
       ding hashes in SNARK circuits. It is memory-efficient, parallelizable, and plausibly
       post-quantum secure, with polylogarithmic proof size and verification. The (low-
       memory) prover requires O(log log n) passes of the input data and its computation
       is dominated by committing to the input witnesses.
           A core component of our construction is a new lattice-based folding scheme that
       compresses a large number of NP-complete statements into one in a single shot.
       Furthermore, we design a generic compiler that converts a folding scheme into a
       SNARK without embedding the Fiat-Shamir circuit into proven statements.

1       Introduction
Succinct non-interactive arguments of knowledge (SNARKs) allow a prover to con-
vince weak devices that a computation was performed correctly using only a short
proof. It has enabled new applications such as scaling and securing blockchain [Whi18;
Xio+23], digital provenance [NT16; DB22; KHSS22; DCB25], verifiable machine learn-
ing [CWSK24; YCBC24], verifiable delay functions [BBBF18], etc. While many effi-
cient SNARKs were introduced [BBHR18; AHIV17; Ben+19; Gol+23; ZCF24; Bre+25;
COS20; BS23; ACFY25], they require massive memory for proving large statements. A
memory-efficient framework splits the computation into small steps and proves each step
separately. Two main strategies exist: streaming provers [BCHO22; PP24; Baw+24] and
incrementally verifiable computation (IVCs) or proof of carrying data (PCDs). Early
IVC/PCD systems rely on recursive SNARKs [Val08; BCTV14], which embed a SNARK
verifier into each statement. The recursion imposes prohibitive overhead and remained
only of theoretical interest.
    Recently, a new framework based on accumulation/folding schemes was introduced
in Halo [BGH19] and further developed in [BCMS20; Bün+21; BDFG21; KST22]. Fold-
ing/Accumulation schemes are a public-coin protocol that reduces the task of checking
multiple uniform statements to checking one, and can be made non-interactive via the
Fiat-Shamir heuristic. By removing the full succinctness requirement, folding schemes
allow more efficient provers and can still serve as a building block for constructing
IVC/PCDs [Bün+21; KST22].
    Before our work, the standard (and the only) framework to leverage folding schemes1
is to construct IVCs/PCDs by folding recursive statements. E.g., in an IVC, at each
iteration step, the prover folds an accumulated statement and an online statement to ob-
tain a new accumulated statement, and it generates a new online statement that checks
a step function and the correctness of the previous folding step. This technique extends
to folding trees (or DAGs) to obtain PCDs. Folding-based IVCs/PCDs is streaming-
friendly, that is, one can start proving without knowing all witnesses upfront. Moreover,
they achieve significant speedups over IVCs/PCDs built from recursive SNARKs, be-
cause the folding verifier circuit is much simpler than a SNARK verifier. However, this
strategy faces a few limitations.

Instantiating random oracles in SNARK circuits. Existing folding schemes re-
quire Fiat-Shamir for non-interactivity, and hash-based folding schemes [BMNW25a;
BMNW25b; BCFW25] invoke even more hashes for Merkle openings. This leads to
efficiency and security concerns for IVC/PCD constructions.
     Efficiency-wise, the folding verifier logic embeds heavy hashing gadgets: A SHA-256
circuit takes tens of thousands of R1CS constraints [Pro]; even a SNARK-friendly hash
takes hundreds of R1CS constraints. Hence, the Fiat-Shamir circuit is dominant in
lattice-based folding schemes [BC24; BC25b; NS25] as it requires hashing elements over

Rq that are much larger than Zq -elements; hash-based folding verifier circuits take even

    Security-wise, hash-based SNARKs and non-interactive folding schemes are only
proven secure in the random oracle model. If we instantiate the oracle with concrete
hash functions and embed it into proven statements, the resulting IVC/PCDs (based on
folding or recursive SNARKs) can be secure only under heuristic conjectures. Notably,
practical attack exist [KRS25] for GKR-based SNARKs if we allow the proven statement
to compute the Fiat-Shamir hash function itself. Although this does not directly affect
folding-based IVC/PCD schemes, it is still a warning sign.

Limited folding arity. Due to the circuit cost of hashing, the folding schemes under-
lying IVCs/PCDs typically take only 2 or 3 inputs per step. Batch proving more input
statements then requires deeper folding trees, which degrades parallelism and security of
IVC/PCD schemes.2 For the schemes that fold more inputs per step [Ngu+24; RZ22],
the embedded folding verification circuit becomes more expensive. We thus ask,

      Rather than using folding schemes for IVC/PCDs, can we leverage folding
      schemes in a different way to obtain memory-efficient proof systems?

1.1    Our Contributions
We re-envision how to use folding schemes introduced in [BGH19; BCMS20; Bün+21].
For the first time, we move away from IVC/PCDs and advocate a high-arity folding
approach. This leads to a new folding-based memory-efficient proving framework without
instantiating random oracles in proven statements.

A new high-arity folding scheme. Our core technical contribution is a new lattice-
based high-arity folding scheme (Theorem 4.1). It is plausibly post-quantum secure, the
proving time is dominated by committing to the input witnesses and running a degree-
3 sumcheck protocol over an extension field, which are standard baseline operations
existing in all prior folding schemes. In comparison, prior schemes such as Lattice-
Fold [BC25a], Neo [NS25], and concurrent works such as Cyclo [GLLO26] and Super-
Neo [NS26] all rely on decomposing witnesses for range proofs, which requires generating
more commitments or running higher-degree sumchecks; LatticeFold+ [BC25b] avoids
witness-decomposition in range proofs but incurs extra costs for double-commitment
transformations. These extra mechanisms significantly increase prover cost and recur-
sive verifier circuit sizes (even if we exclude the Fiat-Shamir circuit) when the folding
arity grows.

SNARKs from high-arity folding. As a second contribution, we develop a generic
framework that converts the high-arity folding scheme into a succinct argument in the

Targeted applications and evaluation. Symphony excels in proving gigantic state-
ments that can be decomposed into many mid-sized uniform statements, where each
uniform statement requires certain range proofs by default. This is the case for applica-
tions such as video editing provenance, post-quantum aggregate signatures, zkVMs, and
verifiable machine learning. E.g., 0xPARC [0xP26] leverages Symphony to verify Llama

     In Section 7, we provide a concrete parameter instantiation and estimate Symphony’s
efficiency in terms of prover operations, SNARK circuit and proof sizes. To prove 216
standard R1CS statements (each with 216 constraints over a 64-bit field), we expect the
resulting proofs to be under 200KB (and under 50KB if post-quantum security is not re-
quired). The prover memory size is independent of the number of R1CS statements, and
the prover time is dominated by approximately 3 · 232 multiplications between arbitrary
elements and low-norm elements over Rq := Zq [X]/⟨X 64 + 1⟩.

Limitations. Symphony is designed as a memory-efficient proof system, not a standard
IVC/PCD scheme. Our main goal is to use folding schemes as a black box to achieve prac-
tical batch-proving while avoiding the heavy recursion overhead in IVC/PCD schemes.
That said, Symphony does not support fully online streaming as in IVC/PCDs, but only
supports small-memory proving via streaming over a known batch of statements. Fur-
thermore, while concretely efficient, the verification complexity of Symphony is linear in
the number of proven statements.
    To achieve full succinctness and streaming, Symphony can be combined with recursive
SNARKs: we partition the online statements into blocks, where each block of ℓnp state-
ments is folded using Symphony, then we apply a recursive SNARK to further absorb
Symphony’s verification logic. This hybrid approach still instantiates random oracles
inside recursive statements, but it is much cheaper than the naive IVC/PCD schemes.

1.2      Technical Overview
Lattice-based high-arity folding. We review a standard folding paradigm from lat-
tice commitments. Consider ℓnp > 1 committed R1CS statements3 , where each
statement consists of a public input Xin and a commitment c (instantiated with module-
based Ajtai hash functions [Ajt96; PR06; LM06]); the relation checks that a message-
opening pair (m, o) is valid for c and (Xin , m) satisfies the corresponding R1CS con-
straints. We fold the ℓnp statements via steps below:
  1. Sumcheck reduction. Standard techniques [Set20; CBBZ23] transform the
     R1CS statements to a sumcheck claim. The prover and verifier then run a sumcheck
     protocol [LFKN92] to reduce the claims into ℓnp linear evaluation statements.
  3
      An R1CS relation is NP-complete and can capture arbitrary computation.

   2. Random linear combination. The verifier samples a low-norm vector β and
      linearly combines the instances via β. The prover similarly combines the wit-
      nesses. By linearity of the evaluation statements and the Ajtai hash function, the
      committed linear relation is preserved after the linear combination.

The key challenge is to prove the low-norm property of witness openings. This is cru-
cial for commitment’s binding property and the folding scheme’s knowledge soundness.
Our design goal is to incur minimal overhead beyond the standard bare-bone folding
mechanism above. This prevents us from using techniques such as witness decomposi-
tion [BC25a; NS25; GLLO26; NS26] and double-commitments [BC25b].

Random projection. LaBRADOR [BS23] adapts the technique from [GHL22], re-
ducing the norm-check of a long vector w to that of a shorter vector Jw mod q, where
J ∈ {0, ±1}λpj ×n is a random matrix. Yet, the verifier time is linear in the witness size
for generating J. Recently, Klooß et al. [KLNO25] introduces a refinement with sublin-
ear verifiers by using a structured projection J := In/ℓh ⊗ J′ , where J′ ∈ {0, ±1}λpj ×ℓh
is a narrower random matrix. The key question now is how to efficiently fold multiple
norm-check statements of the projected vectors into a single linear statement.

mial lookup technique [BC25b]. Let R := Z[X]/⟨X d + 1⟩ be a power-of-two         cyclotomic

ment to a monomial vector g ∈ Rqn , where gi ≈ X fi embeds fi onto exponent for all

a sumcheck-based protocol over a λ-bit field. The prover cost is O(n) Rq -additions.

sends a double commitment c to the d monomial commitments and prove c’s correctness.
However, this technique requires the execution of two extra sumcheck protocols.

    Our norm-check protocol is relatively simple, but the knowledge soundness proof
requires some care. The key challenge lies in ensuring the consistency between the pro-
jected vector w′ = Jw mod q and the monomial vector g. We carefully leverage sum-
check soundness and the algebraic property of tensor of rings (Section 2.3) to reduce the
consistency check to evaluation claims of w and g’s multilinear extensions. To formally
apply sumcheck soundness, the extractor needs to first extract the committed vectors w′
and g via rewinding, and then simulate the malicious prover one more time with fresh
verifier randomness. However, in the last simulation, the monomial commitment and its
underlying vector g′ sent by the prover is unlikely to be the g-vector extracted before,
because the projection matrix J is unpredictable and can lead to a different projected
vector. This makes it difficult to directly apply sumcheck soundness. We address this
issue by carefully designing the extractor, see the proof of Theorem 3.1 for more details.

Prover complexity. As discussed in Remark 4.2, the folding prover requires space
roughly the same as the witness size n of each input statement. As a tradeoff, the
algorithm requires O(log log(n)) passes over the input data. Fortunately, the prover can
start computing the witness commitments without loading the entire witness, and each
subsequent pass takes a smaller amount of data and computation than the previous pass.

From high-arity folding to succinct proofs. For now, the verifier circuit complex-
ity is dominated by the Fiat-Shamir heuristic, which is large with high folding arity ℓnp .
This makes the standard IVC/PCD compiler infeasible. We present a new memory-
efficient paradigm for building folding-based SNARKs without recursively proving hash
computations. Naively, given a folding scheme Πfold , we can apply Fiat-Shamir to ob-
tain a non-interactive folding scheme FS[Πfold ] in the random oracle model. However,
the folding verifier needs to read at least ℓnp committed instances to generate a folding
challenge. That already blows up the proof size for large ℓnp . E.g., for ℓnp = 1000, the
folding proof π easily exceeds 30MB in size with lattice or hash-based schemes.
    We address the proof-size inefficiency by letting the verifier run Fiat-Shamir on a
compressed transcript. The prover first sends short commitments {cfs,i }i to the prover
round messages of Πfold , the verifier then obtains the round challenges using {cfs,i }i
(rather than the original prover messages). Finally, the prover uses a Commit-and-Prove
SNARK (CP-SNARK) to show that the openings of {cfs,i }i gives a valid folding proof
w.r.t. public verifier challenges. Importantly, since the folding challenges are generated
by the verifier, the CP-SNARK statement does not need to prove hash computations.
    In Appendix B, we reduce the knowledge soundness of the compiled non-interactive
protocol (Section 7) to that of the original interactive protocol Πfold , assuming that the
“outer commitment” (for transcript compression) is straightline extractable in ideal-
ized models. Security proofs for non-interactive protocols in the random oracle model
are often more complex. For example, the analysis of the non-interactive version of
LaBRADOR [Aar+24] relies on a sophisticated framework called predicate special sound-


                                            7
ness. Our approach enables a simpler analysis by exploiting the straightline extractabil-
ity of the underlying commitment.
    For better succinctness, we instantiate the “outer commitments” with Merkle hashes
or KZG commitments. Compared to the warm-up, this scheme compresses > 30MB-
sized folding proofs into log(n) Merkle (or KZG) commitments, under 1KB for most
applications. Finally, we also compress the reduced instance-witness pair (xo , wo ) ∈ Ro
of Πfold into a tiny string using standard SNARKs.

Multi-layer folding without recursive circuits. Our instantiation folds 210 R1CS
statements over Rq = Zq [X]/⟨X 64 + 1⟩, equivalent to 216 statements over Zq . Recent
hash-based SNARKs can easily prove more than 224 R1CS constraints in a few seconds.
So we can handle more than 240 constraints in total. In principle, even larger arity is
possible: e.g., a 214 -way folding batches over a million statements, enough to prove a
billion RISC-V instructions if each statement covers a thousand instructions. However,
higher arity increases norm blowup, forcing larger moduli or lattice dimensions, and
requires the CP-SNARK to prove more Rq -multiplications.
     In Section 8, we extend our scheme to higher folding depths. After obtaining the
first layer CP-SNARK proof and the reduced statement (xo , wo ) ∈ Ro , we further split
(xo , wo ) to multiple uniform NP statements. Our high-arity folding scheme, combined
with the commit-and-prove compiler, then reduces these uniform statements again into
a CP-SNARK and a SNARK proof. The final output is two CP-SNARK proofs plus one
SNARK proof. Importantly, we avoid embedding Fiat-Shamir heuristics in circuits.

Extending to other folding schemes. While our compiler naturally extends for
elliptic-curve-based folding schemes (e.g., [BC23; KS24b; KS24a]), it is more nuanced to
compile hash-based folding schemes: although we can move the Fiat-Shamir transform
outside the recursive SNARK circuit, the CP-SNARK statement still needs to check
Merkle-path openings, which accounts for the dominant part of the recursive statement.
That said, efficiently compiling a hash-based folding scheme into a succinct argument
in the random oracle model remains an open problem.

1.3   Comparison with Monolithic SNARKs
Compared to folding-based IVC/PCDs, Symphony enables smaller recursion overhead
and folding depth, and the security can be proven in the random oracle model. While
memory-efficient SNARKs in the random oracle model do exist (e.g.[BCHO22; Baw+24]),
we highlight two advantages of Symphony over monolithic SNARKs:
Modularity. Symphony is more modular and generic, which can combine different fold-
     ing schemes and CP-SNARKs, compared to existing monolithic SNARKs that re-
     quire careful and tailored memory and streaming optimizations. For example, the
     state-of-the-art lattice-based argument, LaBRADOR [BS23], requires the prover
     to compute “cross terms” over all pairs of chunked witnesses, hardening memory
     and streaming optimizations when the number of chunks is large.


                                           8
Scalability. High-arity folding combined with CP-SNARKs scales better for large-scale
     computation. While CP-SNARKs [Kil89; CLOS02; CFQ19] can already prove ℓ
     instance-witness pairs in a batch, their concrete cost is high when ℓ is large. For
     example, the state-of-the-art low-memory SNARK [Baw+24] requires O(ℓn) ex-
     pensive elliptic curve operations; certain hash-based and lattice-based monolithic
     SNARKs allow for fast proof generation on reasonable statement sizes (e.g., 230 ),
     but their performance deteriorate with limited memory and increasing statement
     sizes. For example, Gemini [BCHO22] incurs a quasilinear prover time complex-
     ity to achieve a small footprint; LaBRADOR needs to compute ℓ2 inner products
     (i.e., Ω(nℓ2 ) operations) for the cross terms, which is a big overhead for large ℓ.
     Our approach sidesteps these bottlenecks by shifting the main computational over-
     head to the more efficient folding phase, using CP-SNARKs only for a lightweight
     consistency check between input instances and the folded instance. This reduces
     memory consumption to O(n) and time complexity down to Oλ (ℓn).

1.4   Other Related Work
Lattice double-commitments. Lattice double-commitment schemes such as [BS23;
BC25b] shrink the Fiat-Shamir transcript by decomposing and re-committing the lattice
commitments sent by the prover in each round. Our commit-and-prove compiler shares a
structural similarity but does not require the commitments to be linearly homomorphic.
Moreover, unlike [Aar+24] that analyzes the non-interactive version of LaBRADOR
using the sophisticated predicate special soundness, we provide a simpler security proof
in the random oracle model. Furthermore, our two-layer folding scheme (Section 8)
introduces a new splitting RoK that reduces a single committed linear statement into
multiple “split” statements, which was not known before.

Sumcheck-based folding schemes. Hypernova [KS24b] initiated the use of Sum-
check protocols in folding schemes, which NeutronNova [KS24a] later optimized to sup-
port more inputs without significantly increasing verifier circuit costs. However, both
schemes are based on elliptic curves and are vulnerable to quantum attacks. There
are two types of plausibly post-quantum secure folding schemes. Hash-based folding
schemes [BMNW25a; BMNW25b; BCFW25] achieve asymptotically fast provers but
have expensive folding verifiers due to many Merkle openings. Lattice-based folding
schemes [BC24; BC25b; NS25; FKNP24; GLLO26; NS26] have smaller verifier circuit,
but the range-proof and the Fiat-shamir circuit costs are still bottlenecks, which force
them to use low folding arity under the standard IVC/PCD compiler [Bün+21; KST22].

Security of IVC/PCDs. Standard IVC/PCD compilers only allow for constant fold-
ing depth, meaning that the resulting schemes can fold at most O(1) statements. Re-
cently, Mangrove [Ngu+24] introduces a more efficient compiler from folding schemes,
but it still requires embedding the entire folding verifier circuit (including FS) into each
statement. Chiesa et. al. [CGSY24] provides a tighter security bound for the PCD


                                             9
compiler from recursive SNARKs, though it only applies to SNARKs with straightline
extractors. Several works [CCS22; Che+23] show how to construct PCD in oracle mod-
els without instantiating the oracles. However, they rely on the existence of relativized
SNARKs, which do not exist in the random oracle model [BCG24].

4     High-Arity Folding for NP-Complete Relations
In this section, we present a high-arity folding scheme for committed NP statements.
Section 4.1 introduces a generalized committed R1CS relation designed for real-world
applications, particularly SIMD (Single Instruction Multiple Data) computations. Sec-
tion 4.2 then describes an interactive folding protocol that compresses a large number
(e.g. 1024) of generalized R1CS statements. Later in Section 5, we will provide a generic
paradigm to transform these interactive folding protocols into non-interactive ones.

Remark 4.2 (Memory Efficiency). We describe a prover algorithm for Πfold with roughly
the same memory cost as running a single Πgr1cs instance with witness size n. As a
tradeoff, the prover takes O(log log(n)) passes to the input data.
   1. The algorithm starts by computing the ℓnp input commitments in a stream and
      obtains the first-round random challenges.
   2. Once getting the random combiner α, the prover executes the sumcheck using the
      algorithm from Section 4 of [Baw+25]. For each of the O(log log(n)) passes over the
      input data, the prover computes the sumcheck evaluation table by linearly com-
      bining the table of each instance. The sumcheck prover takes time O(n log log(n))
      plus the cost of combining the ℓnp evaluation tables, where the latter is dominant.
      We refer to [Baw+25, Section 4.3] for more details.
   3. After executing the sumcheck and deriving the folding challenge β, the prover
      streams the input witnesses again and combines them into a single folded witness.

In this section, we introduce a two-step compiler to make Πfold non-interactive via the
Fiat-Shamir transform. The compiler is a generic extension to the ideas behind Pro-
tostar [BC23] and lattice double-commitments [BS23; BC25b]. Notably, our scheme
removes the need for the “outer commitments” to be linearly homomorphic. More-
over, unlike [Aar+24] that analyzes the non-interactive version of LaBRADOR using
the sophisticated predicate special soundness, we provide a simpler security proof in the
random oracle model.

6    SNARKs in the ROM from High-Arity Folding

scheme Section 4 and combine this with a Commit-and-Prove-SNARK (Definition 2.8)
to construct a succinct proof system in the random oracle model for batch-proving many
R1CS statements.
    Unlike folding-based IVCs and recursive SNARKs, our approach avoids instantiating
random oracles in SNARK circuits and requires only a single folding step. The scheme
inherits plausible post-quantum security from the underlying SNARKs. When using
hash-based (or pairing-based) SNARKs, the proof size is independent of the number of
R1CS statements and grows poly-logarithmically with the per-statement witness size.
Compared to monolithic CP-SNARKs, our approach leverages the folding scheme to
handle the majority of the computational load, and the CP-SNARK is only used to
prove a small recursive verifier statement.

   • Given the ℓ · kb linear statements in R′ , we use the high-arity folding scheme and
     the commit-and-prove compiler again to compress them into a CP-SNARK proof
     and a SNARK proof. Since the input statements are already linear, the high-arity
     folding scheme does not need to run the Hadamard protocol (Figure 1). Moreover,
     in addition to the folding-verifier logic, the CP-SNARK relation also ensures that
     the verifier checks in both the splitting RoK and the decomposition RoK pass.

      With the commit-and-prove technique, the CP-SNARK circuits only checks linear
      combinations, not the Fiat-Shamir heuristic or commitment opening relations.
Compared to the single-layer folding-based SNARK, the CP-SNARK statements in the
two-layer scheme only checks O(ℓnp + ℓ) Rq -multiplications, rather than O(ℓnp · ℓ) mul-
tiplications as in the single-layer scheme. The norm blowup is also significantly smaller,
enabling smaller moduli and lower lattice dimensions. As a tradeoff, the two-layer scheme
relies on a slightly stronger assumption where the MSIS assumption holds even if the
matrix A has the form of Eq. (56). Furthermore, although most 1st-layer sub-protocols
remain memory-efficient and streaming-friendly, the sumchecks become ℓ-times larger.
Naively running them would incur either high computational cost or high memory cost.
Fortunately, again, we can use the technique from Section 4 of [Baw+25] to run the
sumcheck prover in time O(n′ ℓ log log(n′ ℓ)), space O((n′ ℓ)1/k ) with O(k + log log(n′ ℓ))
passes over the input data.

     Our proof relies on the notion of round-by-round soundness [Can+19; CMS19].
A protocol is round-by-round sound if there is a state function over partial transcripts
such that (i) if the instance x is not in the language, then the initial state is doomed; (ii)
in each round, if the current transcript is in a doomed state, then for any next prover
message, with overwhelming probability over the verifier’s challenge, the next state will
still be doomed; and (iii) if the final state w.r.t. the entire transcript is doomed, the
verifier rejects.
